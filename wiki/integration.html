03 · Integration

Writing for Venus OS

Conventions shared by every service in this ecosystem. Follow them and your service behaves like the built-in ones — visible in the remote console, controllable by the ESS, auditable by the policy engine.

D-Bus service naming

Venus OS discovers services by their bus name. The pattern:

com.victronenergy.<type>.<suffix>

com.victronenergy.battery.jbd_mqtt        # dbus-mqtt-battery
com.victronenergy.pvinverter.tasmota      # dbus-tasmota-pv
com.victronenergy.grid.esphome_ct         # dbus-esphome-grid-sensor
com.victronenergy.acload.emporia_vue_1    # dbus-emporia-vue, one per channel

Pick <type> from what Venus OS already understands — battery, pvinverter, grid, acload, solarcharger. A wrong type means the GX ignores your service no matter how correct the paths are.

Paths every service should publish

PathMeaning
/ProductId, /ProductNameIdentity shown in the device list
/ConnectedLiveness — Venus hides services reporting 0
/Status or /ErrorCodeFault visibility without opening logs
Type-specific valuese.g. /Dc/0/Voltage, /Ac/Power, /Soc

MQTT topic conventions

Telemetry mirrors use a stable prefix so subscribers can wildcard safely:

victron/<source>/<device>/<metric>

victron/battery/jbd_1/Soc          # percent
victron/grid/meter_1/Power         # watts, signed
victron/inverter/state             # control-layer state changes
victron/event/dbus                 # dbus-event-log audit stream
  • Retained state topics. Current-value topics publish retained so dashboards render instantly after reconnect.
  • Events are not retained. Audit and event streams replay from storage (SQLite/TimescaleDB), not from the broker.
  • No secrets in topics. ACLs belong in broker config; see fastapi-mqtt-gateway for the authenticated gateway pattern.

Installing as a package

All on-device services ship as Venus OS packages installable via PackageManager or bootstrap.sh. The layout follows the dbus-service-template:

service-name/
├── service/run              # supervise script
├── dbus-service.py          # entry point
├── config.ini               # instance settings
├── install.sh               # idempotent installer
└── README.md

Scaffold a new service instead of hand-rolling the boilerplate:

copier copy https://github.com/4alvit/dbus-service-template my-dbus-service

Rules that keep the fleet debuggable

  • Log to stdout/stderr — daemontools captures it under the service directory; never background yourself.
  • Reconnect loops with backoff — MQTT and D-Bus drop during GX reboots; treat disconnects as normal.
  • One service, one job. Translation, decision-making, and audit live in separate processes (see architecture).
  • Register writes with governance. Any service issuing control commands must route them through venus-os-governance gates so dbus-event-log sees them.
